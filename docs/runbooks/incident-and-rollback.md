# 事故处理与回滚

- 日期：2026-09-24（W0 Day 5 初稿）
- 负责人：本人（单人值守）
- 每个手段的“可用周次”标出了它什么时候真正能用；W7 Day 4 完善，W9 Day 3 演练

## 严重度

| 级别 | 例子 | 响应 |
|---|---|---|
| S1 | 跨租户数据泄露；控制面凭据暴露；数据丢失；大面积不可用 | 立刻处理；必要时停止注册或整站只读 |
| S2 | 发布失败率高；单个功能不可用；恶意站点在传播 | 当天处理 |
| S3 | 小问题、有临时办法 | 排进正常迭代 |

## 第一步：止损

| 手段 | 做法 | 可用周次 |
|---|---|---|
| 暂停单个站点 | Admin 将站点设为 `suspended`（保留证据，不删除） | W7 |
| 停止注册 | 后台开关 | W7 |
| 回滚站点版本 | 把 `current_deployment_id` 改回之前的 READY 部署 | W5 |
| 回滚应用版本 | 在运行平台上回到上一个镜像 / 上一次发布 | 首次部署 staging 时 |
| 撤销用户的所有 Session | 批量把 `revoked_at` 设为当前时间 | W1 |
| 轮换密钥 | 在密钥管理里生成新值 → 重新部署 → 作废旧值 | 首次部署 staging 时 |
| 边界封锁 | 在 Cloudflare 上按 Host、IP 或路径封锁 | W3 |

## 数据库迁移回滚

- 默认**只向前修复**：写一个新的迁移来修正问题，不改已经执行过的迁移文件。
- 会破坏数据的迁移（删列、删表）分两步：先部署不再使用该列的代码，下一个版本再删。
- 迁移出事时：优先向前修复；数据已经损坏就按 [备份与恢复](../ops/backup-and-recovery.md) 执行 PITR。

## 凭据泄露（包括提交到公开仓库）

1. **立即作废**泄露的凭据。只从 git 历史里删掉是不够的：仓库是公开的，泄露的内容可能已经被抓取。
2. 轮换所有可能被连带影响的凭据。
3. 查看访问日志，判断影响范围。
4. 从 git 历史里清除（可选；前提是凭据已经作废）。
