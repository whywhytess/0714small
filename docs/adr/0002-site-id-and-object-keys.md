# 0002. 不可变 site_id 与对象键

- 状态：提议
- 日期：2026-09-24

## 背景

slug（子域名）以后可能允许修改，被删除后也可能被别人重新注册。如果对象键或授权依赖 slug，改名或复用 slug 时就可能读到别人的文件，或留下孤儿对象。

## 决定

1. `sites.id` 是 UUID，创建时生成，**永不改变、永不复用**。所有授权、外键和对象键都用 `site_id`，不用 slug。
2. slug 只用于 Host 解析：Gateway 先把 Host 解析为 `site_id`，之后的所有查询都按 `site_id` 进行。
3. 对象键格式：

   ```
   sites/<site_id>/blobs/<blob_id>
   ```

   - `blob_id` 是每次写入时新生成的随机 ID（UUIDv7 或 128 位随机数）。
   - 对象写入后**不再覆盖**。编辑文件就是写一个新对象，再让 `draft_files.object_key` 指向它。
   - 对象键里不包含用户提供的路径或文件名，避免路径注入和超长键。
4. 用户可见的路径只存在于数据库（`draft_files.path`、`deployment_files.path`），先经过统一的规范化函数（W2 Day 2，TS 与 Go 共用 `packages/contracts` 中的测试向量）。
5. 草稿和部署引用的是同一批不可变对象。发布只生成清单，不复制对象（见 ADR 0006）。
6. 清理任务只删除**不被任何草稿和保留期内部署引用**、且已经超过宽限期的对象。

## 后果

- 发布成本与文件数量成正比，与文件大小无关。
- 同名覆盖会留下旧对象，需要清理任务和存储配额把它们计算进去。
- 以后要做内容去重（按哈希），可以在不改变这个格式的前提下加入。

## 被否决的方案

- **`<slug>/<path>` 作为对象键**：改名、复用 slug、路径编码都会出问题。
- **每次发布复制整个目录**：文件多时又慢又贵，复制中途失败还会留下半成品。
